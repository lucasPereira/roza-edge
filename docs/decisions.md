# Decisions

This append-only log records decisions adopted by Róża Edge. Dates indicate when
entries were recorded; the initial entries document decisions already applied
before this log was created. Existing decisions remain unchanged except for
relationship links to decisions that supersede, amend, or extend them, and the
corresponding links back to earlier decisions.

## 0001 - Start Róża Edge as a separate implementation - 19/11/2026

Róża Edge is a new implementation of the test code refactoring framework
developed for Lucas's doctorate. It has its own Git repository, included as a
submodule of the doctorate workspace, so its development can proceed
independently from the legacy and modern implementations while preserving those
implementations for reference.

## 0002 - Organize the repository into modules as needed - 19/11/2026

- **Extended by:** [0005](#0005---define-the-repository-structure---19112026)

Róża Edge uses a Gradle multi-project build with modules at the repository root
and common build configuration in the root build script. The only included
module is currently `spikes`, which contains the technology prototypes. Engine,
backend, frontend, and experiment modules will be added when their work begins,
avoiding empty modules and configuration without a current purpose.

## 0003 - Keep subjects as independent Git submodules - 19/11/2026

The `subjects/` directory contains projects used to evaluate refactorings. Both
controlled examples and real-world projects belong there as Git submodules,
allowing Róża Edge to record the subject revisions used in its evaluation.
Subjects remain outside the root Gradle build and retain their own build
configuration. The first subject is `university-system`, a controlled example
whose domain gives the test scenarios meaningful names.

## 0004 - Guide agents with specific code generation rules - 19/11/2026

Lucas was frustrated by code generated by agents that was difficult to read,
including awkwardly wrapped declarations and dense expressions. General
instructions to produce readable code left too much room for interpretation and
led to repeated corrections. The decision is to guide agents with specific rules
in the [Code readability](../AGENTS.md#code-readability) section of `AGENTS.md`,
based on concrete problems encountered during development.

These rules guide code generation and editing through explicit requirements for
variable types, spacing around wrapped declarations, extracting stream pipelines
from conditions, and string interpolation. Palantir remains responsible for
automatic formatting, but formatting alone cannot resolve every readability
issue. The agent instructions address how code is written before the formatter
lays it out.

## 0005 - Define the repository structure - 19/11/2026

- **Extends:** [0002](#0002---organize-the-repository-into-modules-as-needed---19112026)

The future engine, backend, frontend, and experiments will each have their own
folder at the repository root, alongside `spikes/` and `subjects/`. The engine
and backend will be Gradle subprojects: the engine provides the refactoring
code, and the backend exposes it to the frontend. The frontend's technology and
build configuration remain undecided. Spikes share one Gradle subproject, and
experiment runners will share another. These folders are added when their work
begins. The root `docs/` folder holds project-wide documentation, including this
decision log.

The following hypothetical tree illustrate the layout:

├── settings.gradle.kts
├── docs/
│   └── decisions.md
├── engine/
│   ├── build.gradle.kts
│   └── src/
├── backend/
│   ├── build.gradle.kts
│   └── src/
├── frontend/

│   ├── README.md
│   ├── reports/
│   │   └── 001-scientist.md

Spikes receive sequential identifiers and scientist codenames; experiments
receive sequential identifiers and philosopher codenames. Identifiers appear in
documentation filenames and result directory names, such as `001-scientist.md`
and `001-philosopher/`. Java packages use only the codename, because a package
segment cannot begin with a number.

The spike catalog is `spikes/README.md`. It records each spike's **identifier**,
**codename**, and **title**. The title links to its document under
`spikes/reports/<identifier>-<codename>.md`. The document evolves with the
investigation, with Git preserving previous versions. This keeps the module root
compact without creating a directory for a single document. Java code follows
Gradle's `src/main/java/` and `src/test/java/` layout. Each spike uses its
codename beneath `br.dev.lucas.roza.spikes`, with candidate implementations
grouped by tool when needed and a shared acceptance test in the spike's package.
Each investigation is a package within the shared `spikes` module, rather than a
separate Gradle subproject.

The experiment catalog is `experiments/README.md`. It records each experiment's
**identifier**, **codename**, **date**, and **title**. The date refers to the
currently recorded result. The title links to the experiment's `README.md` under
`experiments/results/<identifier>-<codename>/`. Runner code belongs under
`experiments/src/main/java/`, with one package per experiment beneath
`br.dev.lucas.roza.experiments`. Runners can depend on the spikes module and
later on the engine to invoke their code directly, without giving each
experiment its own Gradle subproject. Each experiment keeps its documentation
and persisted outputs together under
`experiments/results/<identifier>-<codename>/`. Generated output files sit
beside the `README.md`. Each rerun replaces its previous generated outputs and
updates the documentation and catalog date, while Git preserves earlier
versions. Subjects remain independent pinned submodules as described in
[0003](#0003---keep-subjects-as-independent-git-submodules---19112026).

Spike and experiment documents briefly introduce the scientist or philosopher
behind their codename directly below the title, followed by a list of their main
ideas and contributions. This introduction has no section heading. Both document
types then use the same four sections. **Context** explains the motivation, the
question being investigated, and the scope. **Subject** describes the project or
code sample and the characteristics relevant to the investigation. **Procedure**
describes what was tried, how it was evaluated, and how to reproduce it.
**Findings** covers the results, limitations, conclusions, and any next steps
supported by the evidence. All four sections are required in every document; use
`<!-- To be completed. -->` as the content of any section that is not ready yet.
